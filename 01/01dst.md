## 2. 优点：它真的做对了什么

### 2.1 把"论文里最难的那句话"写成了代码

立项书 §1.1 的场景是"订单已在服务器创建，但 HTTP 响应超时"。多数原型会假装这是"请求失败"，然后重试。**这个项目没有**：

- `mock/main.go:154-157` 在**副作用提交之后**才断连（`s.inject(w, tool, "after")`），
- `mock/main.go:67-75` 用 `http.Hijacker` 直接 hijack 并关闭连接，制造**真正的"无响应"**而不是返回一个 500，
- `raguard/transport.py:12-14` 把它翻译成 `UncertainResult`（"可能已经提交"），而不是 `Error`。

这三点合起来，才让"不确定提交"成为一个**在实验里可以被观测、被复现的现象**。这是全系列里唯一一个把抽象风险落成可执行事件的实现。

### 2.2 代次隔离（generation fencing）是真并发控制，不是注释

`raguard/ledger.py:125-138` 的 `complete()` 用一条带 `generation=? AND state='in_flight'` 的 UPDATE 做 CAS；`retry_claim()`（`:152-171`）先比对代次再 `generation+1`。效果是**慢执行者不可能覆盖新执行者的结果**，而且有专门的测试证明：

- `tests/test_gateway.py:106-116`：旧代次写回被拒绝，账本仍是新代次的 `confirmed`；
- `tests/test_gateway.py:126-131`：24 个并发请求 × 12 线程，外部执行次数严格为 1；
- `tests/test_gateway.py:133-142`：8 个并发补偿只有 1 个成功。

这类测试很多项目会写"Called once"就交差，它是用**真实线程池 + 真实 SQLite** 打的。

### 2.3 状态机语义克制且自洽

| 状态 / 证据 | 动作 | 代码位置 |
|---|---|---|
| 同一意图已确认、结果可验证 | Replay | `gateway.py:39-48` |
| 超时但正向回读证实成功 | Reconcile + Replay | `gateway.py:52-55` |
| 不可确认且只读/稳定幂等 | 最多两次安全调用 | `gateway.py:71`、`:89-90` |
| 不可确认且不可安全重试 | Stop | `gateway.py:58-60` |
| 可补偿写 + 人工批准 + 无未解决下游 | 单次补偿认领 | `ledger.py:182-199` |

而且 `claim_compensation()` 会先扫一遍**下游依赖**，只要发现任何 `in_flight/confirmed/unknown/compensating` 的下游引用了本步骤，就直接 `Conflict`（`ledger.py:189-193`）——"不能单独补偿上游"这句论文级的不变量，是被代码强制执行的。

### 2.4 边界声明比方法本身更值钱

`docs/DESIGN.md:35-42` 的"不能声称的事情"写了 6 条，其中两条尤其难得：

> `readback` 只能确认证据为正；查不到**不能证明没执行**。

> **不保证通用 exactly-once**。沙箱的幂等写由 Go 服务强制保障；真实服务未必支持。

审稿人最爱问的"你的 exactly-once 从哪来"，这里提前自己回答了。**这是我认为这一份最强的部分**：它知道自己不可能证明什么。

### 2.5 安全默认值到位

- 工具性质由**管理员注册表**给出，Agent 不能自称可重试（`policy.py:1` 注释、`:26-31`）；
- 未知工具一律 403（`gateway.py:33-34`）；
- HTTP 只监听 `127.0.0.1`（`http.py:72-73`），上游地址被白名单化到回环端口（`transport.py:17-26`）；
- 访问日志不写请求体（`http.py:18-20`），账本事件不记参数与响应体（`ledger.py:81-83`）；
- 响应体超过 64 KB 直接当"不确定"处理，避免把任意数据落盘（`transport.py:39-45`）。

## 3. 缺点：问题在哪

### 3.1 研究设计层（最致命）

**(1) 一条基线都没有，一个指标都没有。**
立项书 §4.2 列了 B0–B6 六组基线，§4.3 列了 8 个指标（TSR / Unsafe Side-Effect / Recovery / Ambiguous-Commit / Overhead / Tail Latency / Escalation / False-Safe）。**代码里一个都没有实现**。`docs/QUALITY.md` 的全部"证据"是"17 项测试通过"。测试通过只能证明"代码按作者的意图工作"，不能证明"方法比固定重试更好"。这是**研究原型和工程原型的分界线**，目前它还在工程侧。

**(2) 论文的三个核心假设，对应代码里只有 if/else。**
立项书 H1/H2/H3 讲的是"证据约束的恢复动作选择"、可学习的风险校准（v1 contextual bandit）、依赖感知的局部恢复（v2 因果图）。实际实现是：

- `policy.py` 全文 31 行，4 个工具 × 4 类效果；
- `gateway.py:36-67` 一串 if/else 分支。

这不算错（文档也说了 v0 就是规则版），但**文档里"主创新点"和代码里"已实现"之间的距离必须显式承认**。现在的 `DESIGN.md:3` 只说"选取其中 v0"，读者容易误以为 v1/v2 在路线图里就会自然长出——实际上从 4 条 if 到"可校准决策器"是一个独立课题。

**(3) 幂等键的语义把安全责任推回给了调用方。**
`model.py:67-71`：

```python
stable_key = sha256([tenant, principal, task, intent])   # 不含 step，不含 fingerprint
```

后果：**只要 Agent 换一个 `intent` 字符串，同一笔业务动作就能再写一次**。账本靠 `PRIMARY KEY(tenant, task, intent)` 去重（`ledger.py:26`），也就是说"这两次调用是不是同一个业务意图"这个判断**完全由调用方命名决定**。

而这恰好是立项书 §2.2 自己警告的事：

> `logical_intent_id` 是经过业务约束定义的**逻辑动作 ID**，**不能仅靠 LLM** 对两段自然语言算一个相似度就断定它们是同一业务动作。

代码没有做任何"业务唯一键 → intent"的强绑定，也没有"同一业务键注册到第二个 intent"时报警。**建议补一条攻击用例：同一笔订单换 intent 名连提两次，看网关是否放行。** 我预判会放行。

**(4) 回读不可用时，连"已知的正确答案"都拒绝返回。**
`gateway.py:39-48`：`state == confirmed` 且 `policy.readback` 时，网关会**再回读一次**；若回读返回 `None`，直接 409 `unverifiable`。

但"回放一条已经记录在案的确认结果"**不产生任何新的外部副作用**——它只是把账本里的结果返回给调用方。把它和"重新执行"绑在同一个安全门里，会导致：

- `MOCK_DISABLE_READBACK=1` 场景下，任务完成率无谓下降；
- 立项书 §4.4 的 **Ablation B（去掉状态回读）** 会同时改掉两件事（"不能重试"和"不能回放"），消融结论被污染。

正确做法：回读失败时仍可 `replay`，但把 `evidence` 降级为 `receipt_only` 并在响应里标注；把"能否回放"与"能否重试"拆成两个独立判据。

**(5) 没有故障强度网格，所以它跑不出论文要的图。**
`mock/main.go:77-84` 的 `inject()` 只支持"`tool:phase` 命中一次"（`faultFired` 一旦为真就不再触发）。立项书 §4.1 要求 0/1/5/10/20% × 6 类故障 × 3 领域。现在**连 5% 的随机故障都表达不出来**。

### 3.2 代码与工程层

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | 退避是硬编码 `time.sleep(0.02)`，两次上限写死 | `gateway.py:71`、`:90` | 无法与 B2（指数退避 + Retry-After）对照；"时延"不是一个可调变量 |
| 2 | 每次账本操作新开 SQLite 连接，`synchronous=FULL` + `BEGIN IMMEDIATE` | `ledger.py:62-77` | 所有并发被串行化。做 P95/吞吐实验会先撞到数据库，而不是撞到恢复策略 |
| 3 | 测试名与断言矛盾 | `test_gateway.py:83-89`：名字是 `..._can_retry_if_readback_unavailable`，断言却是两次 409、执行次数 1 | 读者会误以为"重试路径"被覆盖，实际它测的是"重试路径不可用" |
| 4 | 没有 principal → tool 的授权关系 | `model.py` 只把 `principal` 当字符串 | 对本题不算错，但一旦要和第三篇的授权网关拼接，就必须补 |
| 5 | 状态转移只存在于 SQL 字符串里 | `ledger.py:128`、`:161` 零散的 `state in {...}` | 没有集中的 `ALLOWED_TRANSITIONS`，也没有模型检查；立项书 §3 里的"TLA+/条件不变式"没有产物 |
| 6 | 读取类结果永久缓存 | `gateway.py:39-48` 对 `inventory.read` 也走 replay | 库存新鲜度问题被 `DESIGN.md:39` 承认，但没有 TTL 机制，消融时无法控制 |

### 3.3 文档与仓库层

- **`research/01_spec.md` 是 `01.md` 的逐字节副本**（37,965 B，SHA-256 相同）。一份 37 KB 的中文立项书塞在代码仓里，会让 grep、代码审查、审稿人浏览都被噪声淹没。
- **`docs/files/` 下 20 个页面是模板化生成的**。例如 `docs/files/raguard_gateway_py.md` 全文只有 4 行通用建议（"先查状态转换和 CAS，复现后补回归测试"），对任何文件都成立。这是**负文档价值**：它让"有文档"这个指标虚高，但读的人拿不到信息。
- `docs/QUALITY.md:3` 自报"Windows 批处理脚本为静态审阅，**未在真实 Windows 系统执行**"。而这个项目的目标读者是 Windows 上的学生——`check_windows.bat` 是他们的第一条命令。
- `README.md:15` 有一句很实用的提醒（"重启 Go 沙箱会清空内存状态，做全新试验时请同时清理 `data/ledger.sqlite3*`"）——这种"踩过坑"的话应该扩散到 `DESIGN.md`，现在藏在最后一段。

## 4. 项目自己已经承认的负结果与红线

它没有假装成功，以下几点是它主动写的，评估时必须记功：

1. **"不保证通用 exactly-once"**（`DESIGN.md:37`）——只承诺条件性安全。
2. **"回读为负不能证明未执行"**（`DESIGN.md:38`）——区分"没有证据"和"证据为否"。
3. **"SQLite 只适用于单机低资源原型"**（`DESIGN.md:41`）——没有拿单机结果冒充分布式。
4. **"审批头是本机演示机制，不是生产身份系统"**（`DESIGN.md:42`）。
5. **一次真实回归事故被记进 QUALITY**（`QUALITY.md:13`：新增"补偿与回放并发"用例后观察到错误的 200，修复为"只有账本原子核对成功才能回放"）。**这种记录比 10 条"全部通过"更有价值。**

| 与 02（路由） | 01 的"效果账本"可以直接当 02 的 `unsafe` 判定器；02 的"验证成本"是 01 的"回读成本"的一般化 |

| 与 04（调度） | 01 的"已发出调用不可取消"正是 04 建模时缺的那块；01 的 `lease_seconds` 可以借用 04 的 deadline 概念 |
| 与 05（根因） | 01 的 `events` 表就是最小 trace；05 的定位结果可以直接作为 01 的"故障分类输入" |

**推荐定位**：**五份里最应该先做、最应该投出去的一份**。目标刊按立项书 §5 的顺序（JNCA → FGCS → JSS），但必须先把 P0-1/P0-2 做完再谈投稿时间。
