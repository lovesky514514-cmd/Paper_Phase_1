## 2. 优点：它真的做对了什么

### 2.1 "全成本记账"是全系列里最完整的一次落地

`runner.py:11-20` 把一次任务的费用拆成**五项**：

```python
model / verifier / router / tool / rework
```

并且每一项都真的在对应位置累加：模型费在 `:90`，验证费在 `_check()`（`:152`），路由税在 `:72`，工具费在 `:120`，失败重做的强模型费进 `rework`（`:102`）。这正好对应立项书 §2.2 那条"费用核算必须说明包含项"的要求。

**这件事的价值在于**：一旦有人问"你的省钱是不是把验证器当成免费的"，代码可以直接指出来"验证器费在 `Cost.verifier` 里单独记"。绝大多数路由原型做不到这一点。

### 2.2 硬约束与软打分严格分离

`policy.py:39-48` 先做**过滤**（预算 / 时限 / 质量下限 / 风险上限），`:49-70` 才做**排序**。这意味着：

- 不会出现"用加权损失函数把风险换掉"的常见错误；
- 拒绝动作是**一等公民**：`_stop()` 返回 `Choice(model=None)`，`runner.py:85-87` 立刻把状态置为 `escalate` 并停止。

立项书 H3 要求"约束而非盲目加权"，代码结构上是遵守的。

### 2.3 "验证是有成本的动作"真的进了决策变量

`Verify` 有三档：`NONE / SCHEMA / CONTRACT`（`model.py:15-18`），各自有独立的**费用**和**延迟**（`config.py:13-14`），而且对 `OPAQUE` 写操作有强制门禁（`policy.py:28-29`、`:36-37`）。

于是"要不要验证"成为一个**会花钱、会变慢**的选择，而不是一个开关。这是本课题相对普通 LLM Router 的正确切入点。

### 2.4 可复现性做到了位

- 合成任务由 SHA-256 派生而非 `random`（`fixtures.py:9-10`），跨机器一致；
- `random` 策略也用哈希而不是 `random`（`policy.py:67-70`），消除测试非确定性；
- `bench.py:70-75` 显式写入一份 `metadata.json`，逐条标注 `"kind": "SYNTHETIC_OFFLINE_REPLAY"`、`"latency": "virtual, not measured P95"`。

这份元数据是"我不会让你误解我的结果"的工程化表达。

### 2.5 `docs/QUALITY.md` 的诚实度是全五份里最高的

`QUALITY.md:12-19` 直接把负结果贴出来，并且明确写：

> **结论：目前没有证明新策略更好，且 `vgr` 在测试集仍发生 2 次业务终态错误；不得称其风险约束已经达到实际安全指标。**

同时 `DESIGN.md:24-26` 主动交代了三处"看起来像作弊的地方"（质量乘积是近似、P95 是预估、`ground_truth_match` 是评估器可见的答案）。**这种自曝在本科项目里非常罕见，应当保留。**

## 3. 缺点：问题在哪

### 3.1 最致命：合成矩阵是自洽循环，"校准"无法被检验

看这三段代码：

```python
# config.py:9-11  —— 路由使用的"模型质量先验"
ModelSpec("S", 0.00035, 24, {"read": .87, ..., "opaque": .66})
ModelSpec("M", 0.0012,  55, {"read": .95, ..., "opaque": .84})
ModelSpec("L", 0.0032, 115, {"read": .99, ..., "opaque": .94})
```

```python
# fixtures.py:16-20 —— 生成"模型实际输出"的阈值
qualities = {
    Effect.READ: (.84, .94, .98),
    ...
}
```

```python
# fixtures.py:30-33 —— 用同一组数字决定这个模型这一次答对还是答错
outputs = {name: expected if _score(...) < threshold else f"wrong-..."
           for name, threshold in zip(("S","M","L"), qualities[kind])}
```

**路由器的先验 = 任务生成器的真值。** 所以：

- 任何"按先验选模型"的策略，在期望上就是最优的；
- 校准误差（ECE / Brier）在构造上恒为 0，立项书 RQ2 想验证的东西**在这套数据上不可能出现**；
- `QUALITY.md` 里"vgr 反而输给 cheapest"的负结果，其实是**这个循环打了自己的脸**：连在"先验=真值"的理想条件下都没赢，说明问题在策略逻辑而不是在数据。

**这是全篇最需要修的一点，且优先级高于任何调参。**

### 3.2 `trusted_contract` 是 oracle，不是契约

```python
# fixtures.py:38
trusted_contract=(kind is not Effect.READ and idx % 7 != 0) or (idx % 5 == 0)
```

这个布尔值跟"业务上是否能拿到可信契约"没有任何关系，是任意构造的。而 `runner.py:157`：

```python
return step.trusted_contract and answer == step.expected   # expected = 标准答案
```

**`CONTRACT` 校验就是拿模型输出和标准答案比。** 所以：

- `CONTRACT` 一旦可用，该步骤就 100% 正确；
- `policy.py:80` 因此把 `risk` 直接置 0：

```python
risk = 0.0 if step.effect is Effect.READ or verify is Verify.CONTRACT else (1 - quality) * step.severity
```

**结论**：只要付 0.0005 美元的"契约费"，风险恒为 0，`risk_limit=0.08` 这个约束永远不 bind，风险约束变成装饰品。`DESIGN.md:26` 承认了这点（"执行前契约直接比较合成标准答案，仅说明接口能表达安全约束"），但**承认不等于解决**——论文里这一条会被直接打回，因为审稿人会问"你的契约从哪来"。

### 3.3 风险模型与模型质量脱钩，等于没有建模

`policy.py:80` 的公式说明了问题：`risk` 只有两种取值——`0`（用了 CONTRACT 或只读）或 `(1-quality)*severity`（其余）。

- 它**不是**"这次调用造成错误外部状态的概率"，只是"模型先验错误率 × 严重度"的乘积；
- 它与 `verify` 强绑定，与"模型-步骤匹配度"、"工具可逆性"、"回滚代价"都无关；
- 立项书 H1 说的是"显式建模调用后外部状态的正确性、错误严重度、恢复代价"——代码只做了"严重度 × 错误率"，后两项缺失。

### 3.4 基线命名与行为不一致，比较结果不可用

| 策略名 | 论文里应该是什么 | 代码实际是什么 | 证据 |
|---|---|---|---|
| `strongest` | 始终用最强模型（B0） | 按 `-quality` 排序，但仍先过**质量门、预算、风险**过滤 | `policy.py:44-48`、`:59-60` |
| `cheapest` | 始终用最便宜模型（B1） | `price + verify_cost` 打分，但同样强制过质量门 → 实际是"过门槛后最便宜的动作" | `policy.py:44-46`、`:57-58` |
| `rules` | 关键词/步骤类型分流（B2） | 按效果类别映射到 S/M/L，**再叠加成本与全部硬门** | `policy.py:63-66` |
| `no_verify_cost` | 消融：不把验证成本计入目标 | 只在**打分**里减掉验证费，**账本仍然计入** | `policy.py:55-56` vs `runner.py:152` |

`QUALITY.md` 里"cheapest 8/12、vgr 7/12"这个对比，比较的其实是"过质量门的最便宜动作"和"VGR 打分"，**都不是论文里那条基线**。审稿人只要看代码就会发现这件事。

### 3.5 12 个测试任务 → 任何 1 个任务翻转就是 8.3 个百分点

`fixtures.py:41` 把 36 个任务按 12/12/12 切分成 train/dev/test。`bench.py:28` 的 `evaluate()` 默认 `split="test"`，于是：

- 主结果只有 **12 个样本**；
- 没有置信区间（`bench.py:42` 只报比例）；
- `dev` 集虽然存在，但 `bench.py`、`README.md` 的默认命令都直接跑 test。

`QUALITY.md:19` 自己也说"应在开发集迭代，再于独立测试集测定"，但工具链的默认行为是把人往反方向推。

## 6. 只改五件事的话

1. 让"先验"和"真值"分开 → 否则一切结果都是同义反复。
2. 让基线名实相符 → 否则"我们更好"无法被验证。
3. 让风险真的会拒绝动作 → 否则 H3 不存在。
4. 12 → 200 个任务 + CI → 否则 8.3 个百分点的噪声里什么都读不出来。
5. 接一次真实模型 → 否则 "token 成本"只是编出来的数。

## 7. 在全系列里的定位建议

| 关系 | 说明 |
|---|---|
| 与 01（恢复） | 01 的效果账本可以直接当 02 的 `unsafe` 判定器——**这是 02 最缺的东西**（现在终态判定用 `step.expected`，等于又一次 oracle） |
| 与 03（授权） | 02 的"opaque 写必须有契约"和 03 的"执行前授权"是同一个思想的两个面；引用时可以互证 |
| 与 04（调度） | 02 决定"用哪个模型"，04 决定"何时执行"；两者的成本模型应当共用一份 `Cost` 结构 |
| 与 05（根因） | 02 的"验证失败率"可以作为 05 的异常特征 |

**推荐定位**：**文献工作做得最好、但最应该"缩题"的一份**。建议把范围从"多模型路由"收缩到**"可获取契约条件下的验证成本感知路由"**，并把 `contract_source` 这条线做成论文的主轴——因为"验证成本"和"契约可得性"是唯一能和 R2-Router / MTRouter / RACER 讲清楚差别的地方。撞题压力最大的部分（"按步骤动态切模型"）应主动放弃。

**风险提示**：立项书 §9 自己也写了"第 2 篇的整体创新压力比第 1 篇还高"。看完代码后我同意，而且更悲观一档：**在"先验=真值"的构造下主方法都没赢，说明策略本身还没有找到真正的增益来源**。
